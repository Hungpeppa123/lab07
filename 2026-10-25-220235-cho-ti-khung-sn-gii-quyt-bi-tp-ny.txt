  Cách chuyển từ C# sang Python
  - abstract class / interface → kế thừa ABC và đánh dấu @abstractmethod.
  - where T : IIdentifiable → TypeVar("T", bound=IIdentifiable).
    AllocationService cũng làm tương tự với bound=TeachingDevice.
  - Predicate<T> / Func<T,double> → Callable[[T], bool] / Callable[[T], float].
  - IReadOnlySet → frozenset. GetAll() trả về tuple để mã bên ngoài không sửa
    được dữ liệu bên trong.
  - Return() đổi tên thành return_device(), vì return là từ khóa của Python.
  - protected set của Status → phương thức _set_status().

> future kia là gì, có chức năng

● from __future__ import annotations thay đổi cách Python xử lý type hint: các
  gợi ý kiểu không còn bị tính ngay khi định nghĩa hàm hay lớp nữa, mà được lưu
  lại dưới dạng chuỗi.

  Vì sao cần

  Bình thường Python sẽ tính type hint ngay lúc chạy tới dòng def. Nếu hint nhắc
  tới một lớp chưa được khai báo thì chương trình báo lỗi:

  class DeviceNotReadyException(Exception):
      def __init__(self, device_id: str, current_status: DeviceStatus):  #
  NameError!
          ...

  class DeviceStatus(Enum):   # khai báo SAU nên Python chưa biết tên này
      ...

  Thêm dòng from __future__ import annotations ở đầu file thì đoạn trên chạy
  bình thường, vì DeviceStatus lúc này chỉ là một chuỗi, chưa cần tồn tại.

  Trong bài này, nó giúp ở mấy chỗ:
  1. Exception nhắc tới DeviceStatus, mà DeviceStatus lại khai báo phía sau.
  2. Lớp nhắc tới chính nó trong hint, ví dụ một hàm trả về TeachingDevice nằm
     ngay trong lớp TeachingDevice.
  3. Bạn được viết T | None thay cho Optional[T], kể cả trên các bản Python cũ.

  Lưu ý
  - Nó chỉ ảnh hưởng tới type hint. Logic chương trình không đổi, và Python vẫn
    không kiểm tra kiểu khi chạy.
  - Dòng này phải đặt đầu tiên trong file, chỉ docstring hoặc comment được đứng
    trước.
  - Từ Python 3.14 trở đi, type hint mặc định đã được tính trễ, nên dòng này gần
    như không còn cần thiết. Giữ lại thì vẫn vô hại và chạy được trên mọi bản.
  - Nếu bạn sắp xếp lớp đúng thứ tự (lớp được dùng khai báo trước) thì có thể bỏ
    dòng này. Nhưng cứ thêm vào cho đỡ phải để ý thứ tự.

● Bước 5 là viết kho lưu trữ generic, nằm ở mục 4 của đề và ô IRepository[T] /
  InMemoryRepository[T] trong UML. Đây là một lớp kho duy nhất nhưng dùng được
  cho mọi loại thiết bị.

  1. Khai báo tham số kiểu

  T = TypeVar("T", bound=IIdentifiable)
  - T là chỗ trống cho kiểu phần tử: lúc dùng có thể là ProjectorRemote,
    WirelessMicrophone, v.v.
  - bound=IIdentifiable nghĩa là T phải là lớp có id. Nhờ vậy, bên trong repo
    bạn được phép gọi item.id một cách an toàn.

  2. Interface IRepository(ABC, Generic[T])

  Gồm 5 hàm abstract, chỉ khai báo chữ ký và chưa có thân:

  ┌────────────┬────────────────────────────────┬───────────────┐
  │    Hàm     │            Tham số             │    Trả về     │
  ├────────────┼────────────────────────────────┼───────────────┤
  │ add        │ item: T                        │ None          │
  ├────────────┼────────────────────────────────┼───────────────┤
  │ remove     │ item_id: str                   │ bool          │
  ├────────────┼────────────────────────────────┼───────────────┤
  │ find_by_id │ item_id: str                   │ Optional[T]   │
  ├────────────┼────────────────────────────────┼───────────────┤
  │ get_all    │ không có                       │ tuple[T, ...] │
  ├────────────┼────────────────────────────────┼───────────────┤
  │ find_all   │ condition: Callable[[T], bool] │ tuple[T, ...] │
  └────────────┴────────────────────────────────┴───────────────┘

  3. Lớp cài đặt InMemoryRepository(IRepository[T])

  Dữ liệu được lưu trong self._items: dict[str, T] = {}, với key là id và value
  là đối tượng.

  ┌────────────┬─────────────────────────────────────────────────────────────┐
  │    Hàm     │                  Quy tắc (mục 4.3 của đề)                   │
  ├────────────┼─────────────────────────────────────────────────────────────┤
  │ add        │ item is None thì ValueError. Id đã có thì                   │
  │            │ DuplicateIdException(item.id). Còn lại thì lưu vào dict     │
  ├────────────┼─────────────────────────────────────────────────────────────┤
  │ remove     │ Có thì xóa và trả về True. Không có thì trả về False, không │
  │            │  raise lỗi                                                  │
  ├────────────┼─────────────────────────────────────────────────────────────┤
  │ find_by_id │ Không có thì trả về None. Gợi ý: dict.get()                 │
  ├────────────┼─────────────────────────────────────────────────────────────┤
  │ get_all    │ Trả về tuple(...), không trả về self._items hay một list    │
  ├────────────┼─────────────────────────────────────────────────────────────┤
  │ find_all   │ Trả về tuple các phần tử mà condition(x) là True. Nên kiểm  │
  │            │ tra condition khác None                                     │
  └────────────┴─────────────────────────────────────────────────────────────┘

  Có 2 điểm cần hiểu:
  - Vì sao get_all trả về tuple? Nếu trả về list hay dict nội bộ, bên ngoài gọi
    .append() hay .clear() sẽ phá hỏng kho mà không qua kiểm tra trùng id. Tuple
    thì không sửa được.
  - Vì sao dùng dict? Tìm và kiểm tra trùng id chỉ mất O(1). dict cũng giữ thứ
    tự thêm vào, nên FirstAvailableStrategy ở bước 6 vẫn có khái niệm "phần tử
    đầu tiên". Đây là phần trade-off cho câu hỏi 4.4.3.

● Bước 6 là viết chiến lược lựa chọn, ứng với mục 5 của đề và nhánh
  ISelectionStrategy[T] bên phải trong UML. Mỗi chiến lược là một cách chọn ra 1
  phần tử từ danh sách ứng viên. Muốn có cách chọn mới thì viết thêm lớp mới,
  không cần sửa code cũ.

  1. Tham số kiểu

  S = TypeVar("S")    # không có bound
  Chiến lược không cần biết phần tử có id hay là thiết bị. Nó chỉ chọn trong một
  danh sách, nên dùng được cho mọi kiểu. Đây là ý của câu hỏi 2.2.6: không phải
  generic nào cũng cần ràng buộc.

  Trong UML vẫn ghi là T. Bạn đặt tên S để không đụng với T đã có
  bound=IIdentifiable ở bước 5.

  2. Interface ISelectionStrategy(ABC, Generic[S])

  Chỉ có 1 hàm abstract:

  ┌────────┬─────────────────────────┬────────┐
  │  Hàm   │         Tham số         │ Trả về │
  ├────────┼─────────────────────────┼────────┤
  │ select │ candidates: Sequence[S] │ S      │
  └────────┴─────────────────────────┴────────┘

  3. Hai lớp cài đặt

  FirstAvailableStrategy(ISelectionStrategy[S])
  - Danh sách rỗng thì raise NoSuitableItemException().
  - Ngược lại trả về candidates[0].

  HighestPriorityStrategy(ISelectionStrategy[S])
  - __init__(self, score_selector: Callable[[S], float]): lưu hàm tính điểm vào
    self._score_selector. Nếu nó là None thì ValueError.
  - select: danh sách rỗng thì NoSuitableItemException, ngược lại
    max(candidates, key=self._score_selector).

  Có 3 điểm cần hiểu:
  - Vì sao truyền hàm tính điểm từ ngoài vào? Như vậy cùng một lớp có thể chọn
    theo nhiều tiêu chí: điểm mặc định, điểm theo phòng
    (get_priority_score_for_room("A203")), chỉ theo pin, v.v. Chiến lược không
    cần biết điểm được tính ra sao.
  - Vì sao dùng max chứ không dùng sort? Đề yêu cầu "chiến lược không thay đổi
    danh sách đầu vào". max chỉ đọc danh sách, còn candidates.sort() thì sửa nó.
    sorted() không sửa danh sách nhưng thừa, vì tốn O(n log n) so với O(n).
  - Hai phần tử bằng điểm nhau thì sao? max trả về phần tử đầu tiên đạt điểm cao
    nhất. Nên biết điều này để giải thích kết quả test.

  4. Đây là chỗ dùng đa hình (2) trong UML

  Ở bước 7, AllocationService chỉ gọi self._strategy.select(...) mà không biết
  đó là chiến lược nào. Gọi change_strategy() lúc chạy thì kết quả đổi theo. Đó
  chính là Strategy pattern, và là câu trả lời cho câu hỏi 2.2.4: dùng interface
  thay vì chuỗi if/else.

  5. Tự kiểm tra

  from models import *
  print(FirstAvailableStrategy().select([3, 9, 5]))                  # 3
  print(HighestPriorityStrategy(lambda x: x).select([3, 9, 5]))      # 9
  print(HighestPriorityStrategy(lambda s: len(s)).select(["a", "abc", "ab"]))  #
  abc → generic, không chỉ thiết bị

  data = [3, 9, 5]; HighestPriorityStrategy(lambda x: x).select(data);
  print(data)  # [3, 9, 5] không đổi

  FirstAvailableStrategy().select([])                                #
  NoSuitableItemException
  HighestPriorityStrategy(None)                                      #
  ValueError

  mics = [WirelessMicrophone("M1","M","C",70,50),
  WirelessMicrophone("M2","M","C",95,80)]
  print(HighestPriorityStrategy(lambda d:
  d.get_default_priority_score()).select(mics))  # M2

● Bước 7 là viết AllocationService, ứng với mục 6 của đề và ô xanh lá ở giữa
  UML. Đây là lớp ráp repository và strategy lại để cấp phát thiết bị. Nó chỉ

  1. Tham số kiểu

  Ở đây bound là TeachingDevice chứ không phải IIdentifiable, vì service cần gọi
  is_ready_for_use(), borrow() và return_device(). Những hàm này chỉ thiết bị

  Như vậy mỗi tầng chỉ đòi đúng thứ nó dùng:

  ┌───────────────────────┬────────────────┬─────────────────────────────────┐
  │          Lớp          │   Ràng buộc    │              Lý do              │
  ├───────────────────────┼────────────────┼─────────────────────────────────┤
  │ InMemoryRepository[T] │ IIdentifiable  │ chỉ cần .id                     │
  ├───────────────────────┼────────────────┼─────────────────────────────────┤
  │ ISelectionStrategy[S] │ không có       │ chỉ chọn trong danh sách        │
  ├───────────────────────┼────────────────┼─────────────────────────────────┤
  │ AllocationService[D]  │ TeachingDevice │ cần mượn, trả, kiểm tra sẵn     │
  │                       │                │ sàng                            │

  2. Các thành phần (theo UML)

  ┌─────────────────────────────────┬────────────────────────────────────────┐
  │           Thành phần            │              Việc cần làm              │
  ├─────────────────────────────────┼────────────────────────────────────────┤
  │                                 │ Một trong hai là None thì ValueError.  │
  │ __init__(repository, strategy)  │ Lưu vào self._repository và            │
  │                                 │ self._strategy                         │
  ├─────────────────────────────────┼────────────────────────────────────────┤
  │ strategy (property chỉ đọc)     │ Trả về self._strategy                  │
  ├─────────────────────────────────┼────────────────────────────────────────┤
  │ change_strategy(new_strategy)   │ None thì ValueError, còn không thì gán │
  │                                 │  chiến lược mới                        │
  ├─────────────────────────────────┼────────────────────────────────────────┤
  │                                 │ Lấy từ repo các thiết bị               │
  │ find_candidates(condition=None) │ is_ready_for_use() và thỏa condition   │
  │                                 │ (nếu có). Trả về tuple                 │
  ├─────────────────────────────────┼────────────────────────────────────────┤
  │                                 │ find_candidates, rồi                   │
  │ allocate(condition=None)        │ self._strategy.select(...), rồi        │
  │                                 │ borrow(), cuối cùng trả về thiết bị    │
  ├─────────────────────────────────┼────────────────────────────────────────┤
  │                                 │ find_by_id. Nếu None thì raise lỗi (ví │
  │ return_device(device_id)        │  dụ DeviceManagementError). Còn không  │
  │                                 │ thì gọi device.return_device() rồi trả │
  │                                 │  về thiết bị                           │
  └─────────────────────────────────┴────────────────────────────────────────┘

  Gợi ý cho find_candidates: chỉ gọi find_all một lần, với một lambda ghép cả 2
  điều kiện:
  lambda d: d.is_ready_for_use() and (condition is None or condition(d))

  3. Những điểm cần nắm

  - Không dùng isinstance hay chuỗi if/else theo loại thiết bị (mục 6.3 của đề).
    Mọi khác biệt giữa các loại đã nằm trong is_ready_for_use() của từng lớp
    con, và service chỉ gọi hàm đó.
  - Hai chỗ đa hình đều xuất hiện ở đây:
    a. d.is_ready_for_use(): chạy phiên bản của lớp con.
    b. self._strategy.select(...): chạy chiến lược hiện tại.
  - Không gọi select khi danh sách rỗng? Không cần tự kiểm tra, vì strategy đã
    tự raise NoSuitableItemException. Cứ để lỗi đó đi ra ngoài.
  - borrow() vẫn tự kiểm tra lại điều kiện sẵn sàng. Như vậy có 2 lớp bảo vệ, kể
    cả khi ai đó viết một strategy chọn sai.
